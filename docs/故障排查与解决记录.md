## 一、存储与系统启动

### 1.1 TF 卡系统起不来（"变砖"）

**现象**：上电后电源灯亮、蓝色工作灯灭，HDMI 无输出，SSH 连不上。

**排查**：
- 把 TF 卡插到笔记本，`lsblk` 能看到 8 个分区，rootfs（ext4）可以正常挂载，数据完整；
- 卡上 `/boot` 为空 —— 这与 eMMC 系统一致，是 RK 镜像的正常状态，**不是损坏**；
- rootfs 里 `syslog` 最后一条记录到某个时刻戛然而止，没有正常的 shutdown 记录 → 硬件断电。

**结论**：数据没丢，问题在 **boot 分区（FAT, 64MB）或 uboot 分区**。

**教训**：TF 卡/eMMC 出问题第一步不是重刷，而是**先把 rootfs 挂载取数据**。

---

### 1.2 从损坏的卡里抢救数据

```bash
# 1. 插上卡，找到设备（通常是 /dev/sda）
lsblk -o NAME,SIZE,FSTYPE,LABEL,PARTLABEL,MOUNTPOINT

# 2. 挂载 rootfs（图形界面一般会自动挂到 /media/$USER/<uuid>）
#    手动挂载：
sudo mkdir -p /mnt/robot && sudo mount /dev/sda8 /mnt/robot

# 3. 只拷需要的东西（不要整盘拷，.vscode-server 有 3.7G 小文件，会卡死）
rsync -a --no-o --no-g /mnt/robot/home/kickpi/ros2_ws/src ~/backup/
rsync -a --no-o --no-g /mnt/robot/home/kickpi/{maps,can,robot_web} ~/backup/
rsync -a --includes='*.sh' --includes='*.py' --exclude='*' \
      /mnt/robot/home/kickpi/ ~/backup/
```

**踩坑**：直接 `rsync` 整个 home 会在 `.vscode-server`（几万个小文件）处进入 `D` 状态卡住十几分钟。**一定要排除它**。

### 1.3 eMMC 系统 SSH 只允许公钥登录

**现象**：知道机器人密码，但 `ssh kickpi@192.168.3.100` 一直 `Permission denied`。

**诊断**：
```bash
ssh -vv kickpi@192.168.3.100
# 关键输出：
# debug1: Authentications that can continue: publickey
```

**原因**：`sshd_config` 里 `PasswordAuthentication no`，只接受公钥。

**当时可用的通道**：
| 通道 | 状态 |
|---|---|
| SSH 22 | 只允许 publickey，无密码登录 |
| FTP 21 | 可登录可读，**但只读**（vsftpd `write_enable=NO`，连 /tmp 都写不了） |
| HTTP 8080 | 静态看板，无上传接口 |

**解决**：在小车本地终端（HDMI + 键盘）执行，把上位机公钥加进去：
```bash
mkdir -p ~/.ssh
echo 'ssh-ed25519 AAAA...你的公钥... user@host' >> ~/.ssh/authorized_keys
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
```

> 也可以改 `/etc/ssh/sshd_config` 打开 `PasswordAuthentication yes`，但不推荐（每次都要输密码，脚本无法自动化）。

---

### 1.4 上位机 SSH 配置（VSCode Remote-SSH 用）

`~/.ssh/config`：
```ini
Host kickpi-robot 192.168.3.100
    HostName 192.168.3.100
    User kickpi
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

**踩过的坑**：原配置里用户名写成了 `kickipi`（多一个 i），VSCode 一直连不上，但报错不明显。

**排查命令**：
```bash
ssh -v kickpi-robot      # 看实际用的是哪个用户名/密钥
ssh-keyscan -t ed25519 192.168.3.100 >> ~/.ssh/known_hosts   # 免去 yes/no 询问
```

## 二、CAN 总线启用（最容易变砖的地方）

### 2.1 背景

C30D 底盘走 CAN，接线用 40Pin 的 **CAN1_M0 = pin 3/5**（GPIO1_A0/A1）。
但原厂 DTB 里 CAN1 是 `disabled`，且 `pinctrl` 指向 **M1** 引脚（pin 19/23）。
所以必须改 boot 分区里的设备树。

**关键难点**：U-Boot 用的不是 FIT 里的 fdt 组件，而是 `resource` 组件里的板型 DTB。

---

### 2.2 版本 1（失败）：只改 DTB + 更新 FIT 哈希

**做法**：解编译 DTB → 改 `can@fe580000` 的 `status`/`pinctrl-0`，关闭 `i2c@fe5c0000` → 重新编译 → 更新 FIT 里 fdt 和 resource 两个组件的 sha256。

**现象**：重启后 **kernel panic**：
```
DTB: rk-kernel.dtb
HASH(c): error
Invalid DTB hash !
No valid DTB, ret=-22
...
rockchip-pm-domain: failed to get ack on domain 'npu', target_idle = 0, val=0x6
Kernel panic - not syncing: panic_on_set_idle set
```

**原因**：
- eMMC 的 boot 分区里有 **14 个 resource 条目**（12 个 DTB + 2 个 logo.bmp）；
- 每个条目的 `ENTR` 结构里自带 **SHA1 哈希**（偏移 `+0xE0`，20 字节）；
- 改完 DTB 却没更新它自己的 SHA1 → U-Boot 校验失败 → **拒绝使用正确 DTB**；
- 回退到 FIT 里的默认 DTB（显示配置不对）→ NPU 电源域对不上 → panic。

> 注意：TF 卡那张镜像只有 3 处 DTB，eMMC 这张结构不同，**不能照搬**。

---

### 2.3 版本 2（失败）：更新 SHA1，但 pinctrl 引用不存在的节点

**做法**：补上每个 ENTR 的 SHA1 + 更新 resource 组件哈希，`pinctrl-0 = <0x23e>`。

**现象**：能启动，但 `can0` 不出现：
```
rockchip_canfd fe580000.can: prop pinctrl-0 index 0 invalid phandle
```

**原因**：`0x23e`（can1m0-pins 的 phandle）**只存在于 FIT 的 fdt 里**，resource 里的板级 DTB 根本没有这个节点，phandle 值也对不上。

---

### 2.4 版本 3（失败）：往 DTB 里插新节点

**做法**：在 `pinctrl` 的 `can1` 节点下插入 `can1m0-pins { rockchip,pins = <...>; }`。

**现象**：全部跳过，一个都没改：
```
! 新 DTB 更大 (113457 > 113377)，跳过
```

**原因**：resource 条目的大小是**预先分配好的**，插入节点让 DTB 大 80 字节 → 超出预留空间 → 无法写回。

---

### 2.5 版本 4（成功）：复用现有节点，只改引脚定义

**核心思路**：**不新增任何节点**，直接复用已经存在的 `can1m1-pins` 节点：
- 把它的 `rockchip,pins` 从 M1 引脚改成 M0 引脚；
- 节点名改成 `can1m0-pins`（长度相同，不影响大小）；
- `can@fe580000` 原本的 `pinctrl-0` 指向这个节点，无需改动；
- `status` 改 `okay`，`i2c@fe5c0000` 改 `disabled`；
- 重新计算该 DTB 的 SHA1 写回 ENTR，更新 resource 组件 SHA256。

```dts
/* 改之前（M1：GPIO4_C2/C3，func 3） */
can1m1-pins { rockchip,pins = <0x04 0x12 0x03 0x11b 0x04 0x13 0x03 0x11b>; };

/* 改之后（M0：GPIO1_A0/A1，func 3） */
can1m0-pins { rockchip,pins = <0x01 0x00 0x03 0x11b 0x01 0x01 0x03 0x11b>; };
```

**结果**：
```
共修改 12 个 DTB
FIT resource SHA256 已更新 @0x2F4
自检: 12 个 DTB 的 SHA1 全部一致
```
重启后 `can0` 正常出现，收到底盘 `0x101/0x102/0x103`。

脚本：`~/can/make_boot_can1_v4.py`

---

### 2.6 救命流程：U-Boot 恢复 boot 分区

补丁失败导致起不来时，**不需要重刷系统**：

**第一步：串口进 U-Boot**
```bash
# 上位机
sudo chmod a+rw /dev/ttyUSB0
python3 capture_serial.py /dev/ttyUSB0 1500000   # 一边抓日志一边发 Ctrl-C
# 另一路持续发 Ctrl-C，然后按板子 RESET
# 看到 => 就是进 U-Boot 了
```

**第二步：用 UMS 把 eMMC 挂成 U 盘**（U-Boot 命令行）
```
ums 0 mmc 0
```

**第三步：上位机 dd 写回**
```bash
lsblk                     # 找到新出现的 29.1G UMS 磁盘，假设是 /dev/sda
sudo dd if=boot_emmc_orig.img of=/dev/sda3 bs=1M conv=fsync status=progress
sync
sudo md5sum /dev/sda3     # 与源文件比对
```

**第四步：退出 UMS 并重启**（U-Boot 里 Ctrl-C 退出后）
```
reset
```

**必备文件**：
| 文件 | 说明 |
|---|---|
| `boot_emmc_orig.img` | eMMC boot 分区**原样**（64MB），回退用 |
| `boot_emmc_can1_v4.img` | 打好 CAN M0 补丁的版本 |
| `make_boot_can1_v4.py` | 生成脚本 |

> 写入目标分区：`/dev/sda3`（PARTLABEL = `boot`，64MB，起始 LBA `0x8000`，长度 `0x20000` 扇区）

---

### 2.7 常见误解澄清

| 误解 | 事实 |
|---|---|
| "我直接拔电源把 boot 拔坏了" | 不是。写完 boot 后做过 `conv=fsync` + `sync` + 回读校验，且成功重启过一次。直接拔电最多影响 rootfs（ext4 recovery），不会改已写入的 boot 内容 |
| "接口名应该是 can1" | 是 **`can0`**。因为 DT 里 CAN0 节点是 disabled，Linux 按注册顺序把 CAN1 命名成了 can0 |
| "CAN1_M0 和 M1 引脚可以随便选" | M0（pin 3/5）和 I2C3_M0 共用**同一组引脚**，启用 CAN 必须关掉 I2C3 |

## 三、ROS 2 环境搭建

### 3.1 eMMC 上安装 ROS 2 Jazzy（arm64）

**踩坑**：
- GitHub raw 在本网络超时 → 用**清华镜像**；
- 系统没有 `ros2` 源，要先加 key 和 source list；
- `unattended-upgrades` 会抢 dpkg 锁，要先禁用；
- eMMC 剩余空间有限（29G），装 `ros-base` 而不是 `desktop`（不需要 RViz，RViz 在上位机跑）。

```bash
# 关键步骤
sudo systemctl disable --now unattended-upgrades
curl -fsSL https://mirrors.tuna.tsinghua.edu.cn/rosdistro/ros.key \
  -o /usr/share/keyrings/ros-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] \
  https://mirrors.tuna.tsinghua.edu.cn/ros2/ubuntu noble main" > /etc/apt/sources.list.d/ros2.list
sudo apt-get update
sudo apt-get install -y ros-jazzy-ros-base ros-jazzy-navigation2 ros-jazzy-nav2-bringup \
  ros-jazzy-slam-toolbox ros-jazzy-robot-localization ros-jazzy-rmw-zenoh-cpp \
  ros-jazzy-foxglove-bridge ros-jazzy-cv-bridge ros-jazzy-v4l2-camera \
  python3-colcon-common-extensions can-utils v4l-utils
```

脚本：`~/install_ros2_emmc.sh`

### 3.2 `jy901_imu` 包找不到（AMENT_PREFIX_PATH 问题）

**现象**：
```
$ ros2 run jy901_imu jy901_node
Package 'jy901_imu' not found
```
但 `~/ros2_ws/install/jy901_imu/share/jy901_imu/package.xml` 明明存在，且 colcon 编译成功。

**原因**：`ament_python` 类型的包（`setup.py`）在 `--symlink-install` 下不会自动把自身加入 `AMENT_PREFIX_PATH`，只有带 `environment/ament_prefix_path.dsv` 钩子的包才会。

**解决**：手动补
```bash
# ~/rosenv.sh 里加一行
export AMENT_PREFIX_PATH=/home/kickpi/ros2_ws/install/jy901_imu:$AMENT_PREFIX_PATH
```

**验证**：
```bash
ros2 pkg executables jy901_imu   # 应输出: jy901_imu jy901_node
```

### 3.3 slam_toolbox 参数文件路径错误

**现象**：
```
Couldn't parse params file '/home/kickpi/ros2_ws/install/share/wheeltec_slam_toolbox/config/...'
```

**原因**：`--symlink-install` 下 install 布局是 `install/<包名>/share/<包名>/...`，而脚本里写的是 `install/share/<包名>/...`。

**解决**：
```bash
sed -i 's|install/share/wheeltec_slam_toolbox|install/wheeltec_slam_toolbox/share/wheeltec_slam_toolbox|' ~/robot_start.sh
```

### 3.4 编译 OOM

**现象**：`gmake: Terminated`、编译中途被杀。

## 四、传感器与外设

### 4.1 udev 设备名乱跳

**现象**：重启或换 USB 口后 `/dev/ttyUSB0/1` 互换，雷达和 IMU 串了。

**原因**：两个设备都是 CH340（`1a86:7523`），没有唯一序列号。

**解决**：按**控制器名**匹配，不用 `xhci-hcd.N`（改 DTB 后编号会变）。

`/etc/udev/rules.d/99-robot.rules`：
```udev
# STM32 底盘 (CH9102F, 有唯一序列号)
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d4", \
  ATTRS{serial}=="597B019116", SYMLINK+="wheeltec_controller", MODE="0666"

# RPLIDAR A1 (Type-C / usbdrd 口)
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
  ENV{DEVPATH}=="*/usbdrd/*", SYMLINK+="rplidar", MODE="0666"

# JY901 IMU (USB3.0 Type-A / usbhost 口)
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
  ENV{DEVPATH}=="*/usbhost/*", SYMLINK+="jy901", MODE="0666"
```

生效：
```bash
sudo udevadm control --reload-rules
sudo udevadm trigger --subsystem-match=tty
ls -l /dev/rplidar /dev/jy901 /dev/wheeltec_controller
```

### 4.2 IMU 串口被占用

**现象**：`jy901_node` 日志刷屏：
```
read error: device reports readiness to read but returned no data
(device disconnected or multiple access on port?)
```

**诊断**：
```bash
fuser -v /dev/jy901
# 输出: /dev/ttyUSB0: kickpi 1996 F.... gateway
```

**原因**：eMMC 系统自带的 `industrial-gateway.service`（工业网关项目）一直占着 `/dev/ttyUSB0`。

**解决**：
```bash
sudo systemctl disable --now industrial-gateway gateway-dashboard
```

> 以后要跑工业网关，再 `sudo systemctl enable --now industrial-gateway` 即可。

### 4.3 雷达无应答

**现象**：`rplidar_node` 报
```
Error, operation time out. SL_RESULT_OPERATION_TIMEOUT!
Failed to set scan mode
```

**排查顺序**：
1. **雷达通电了吗、转了吗？** —— 最常见原因。A1 靠 USB 供电，插着线但没接电就完全无应答；
2. 直接探测原始串口：
   ```bash
   python3 ~/probe_lidar.py /dev/rplidar
   # 正常应回: a5 5a 05 00 00 40 81  → "✅ 是 RPLIDAR"
   ```
3. 对比两个口（别开错设备）：
   ```bash
   python3 ~/probe_lidar.py /dev/ttyUSB0
   python3 ~/probe_lidar.py /dev/ttyUSB1
   ```
   雷达回 `a5 5a...`，IMU 回 `55 51 / 55 52 / 55 53` 帧。

**注意**：`scan_mode` 参数在这个驱动版本里不生效，日志始终显示 `Sensitivity, 8 Khz`。转速由雷达成像头自己的固件决定，提高转速后实测 `/scan` 从 10 Hz 提升到 **17 Hz**。

### 4.4 `check_robot.sh` 报 `integer expression expected`

**现象**：
```
/home/kickpi/check_robot.sh: line 29: [: 0
0: integer expression expected
```

**原因**：`pgrep -f` 返回多行结果，被当成一个整数比较。**只是显示问题，不影响实际运行**。

**修法**：改成 `pgrep -cf "模式"` 或 `$(pgrep -f ... | wc -l)`。


### 5.2 systemd 服务反复失败：8080 被旧进程占用

**现象**：`systemctl is-active robot-web` 显示 active，但 `8080` 没有监听，API 访问被拒绝。

**诊断**：
```bash
sudo journalctl -u robot-web -n 20 --no-pager
# OSError: [Errno 98] error while attempting to bind on address ('0.0.0.0', 8080): address already in use
```

**原因**：之前用 `start_web.sh` 手工起过一个实例，它不在 systemd 管理下，一直占着端口；systemd 的新实例绑定失败 → 崩溃 → 无限重启。

**解决**：
```bash
systemctl stop robot-web
for p in $(pgrep -f "robot_web/serve[r].py"); do kill -9 $p; done
systemctl start robot-web
ss -lntp | grep 8080
```

> ⚠️ 用 `serve[r]` 这种方括号写法，避免 `pkill -f` 匹配到自己（见第八章）。

### 5.3 `KillMode=process`（必须加）

**现象**：`sudo systemctl restart robot-web` 之后，通过网页 `/api/start` 拉起的 ROS 全栈全部消失。

**原因**：systemd 默认 `KillMode=control-group`，会杀掉整个 cgroup，包括网页用 `subprocess` 拉起的子进程。`start_new_session` 也逃不出 cgroup。

**解决**：service 里加
```ini
KillMode=process
```

### 5.4 网页服务被 zenoh-router 连带停止

**现象**：`robot-web` 每隔几秒被 Stopping 一次，端口始终不监听。

**原因**：
- `robot-web.service` 里有 `Requires=zenoh-router.service`；
- 而 `zenoh-router.service` 正在**重启循环**（端口 7447 被残留进程占用）；
- 依赖方一停，robot-web 就跟着停。

**解决**：
```bash
systemctl stop zenoh-router
for p in $(pgrep -f "rmw_zenoh[d]"); do kill -9 $p; done
systemctl start zenoh-router
systemctl restart robot-web
```

**经验**：看到某个服务"莫名被停"，先 `systemctl show <svc> -p NRestarts` 看它的依赖是不是在疯狂重启。

## 六、跨机通信（上位机 ↔ 小车）

### 6.1 为什么原来是 Zenoh

项目早期在 Windows/WSL 上开发，Windows 收不到入向 UDP，DDS 组播发现不通。
Zenoh 全程走 TCP，可以绕开这个问题，所以选定了 `rmw_zenoh_cpp`。

### 6.2 现在的问题：跨机发现是单向的

**现象**：
| 方向 | 结果 |
|---|---|
| 小车上 `ros2 topic list` | 能看到笔记本发布的话题 ✅ |
| 笔记本上 `ros2 topic list` | **只看到自己的 `/rosout`** ❌ |
| 笔记本 `ros2 topic echo /scan ...`（显式指定类型） | **能收到数据** ✅ |

**结论**：**数据面通，图（发现）面不通**。

**影响**：

## 八、脚本与工具踩坑

### 8.1 `pkill -f` / `pgrep -f` 自匹配（本节最容易反复踩）

**现象**：执行 `ssh robot 'pkill -f dds_pub.py; ...'` 时，**整条 ssh 命令瞬间断开**（exit 255），后面的命令一句都没执行。

**原因**：`ssh` 在远端执行的命令行本身包含 `dds_pub.py` 这个字符串，`pkill -f` 把它也匹配上了 → 杀掉了自己的 shell。

**解决**：用**方括号**打断字面匹配：
```bash
pgrep -f "robot_web/serve[r].py"     # 匹配 serve.py，但命令行里的 serve[r].py 不含 serve.py 字面
pkill -f "rmw_zenoh[d]"
pgrep -f "dds_p[u]b.py"
```
或者把逻辑写进脚本文件再执行（脚本文件名不会被匹配到）。

> 项目文档里记录的 `pgrep` 自匹配坑（网页控制台显示"永远运行中"）是同一个根源。

### 8.2 heredoc 结束符打错

**现象**：写 `cat > a.py <<'EOS' ... EOS`，但结尾手打成 `EOF` → **后面的 shell 命令全部被吞进文件里**，脚本内容变成一堆 shell 命令。

**症状**：运行时报语法错误，打开文件能看到不该出现的 `scp -q ...` 之类。

**教训**：写多行脚本优先用 `printf '%s\n' '...' '...'` 或先写本地文件再 `scp`，别在一条命令里混 heredoc 和后续命令。

### 8.3 systemd 用户服务缺 ROS 环境（status=127）

**现象**：
```
Process: ExecStart=/opt/ros/jazzy/lib/rmw_zenoh_cpp/rmw_zenohd (code=exited, status=127)
```

**原因**：127 = 找不到命令/动态库。`rmw_zenohd` 依赖 `libament_index_cpp.so` 等，没 `source` ROS 环境时 `LD_LIBRARY_PATH` 不全。

**解决**：
```ini
ExecStart=/bin/bash -lc 'source /opt/ros/jazzy/setup.bash && exec ros2 run rmw_zenoh_cpp rmw_zenohd'
```

### 8.4 串口权限

**现象**：`could not open port /dev/ttyUSB0: [Errno 13] Permission denied`

**解决**（二选一）：
```bash
sudo chmod a+rw /dev/ttyUSB0                 # 立即生效
# 或者持久化：
echo 'SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", MODE="0666"' \
  | sudo tee /etc/udev/rules.d/99-ch340.rw.rules
sudo udevadm control --reload-rules && sudo udevadm trigger
```

### 8.5 Rime 输入法装了却找不到

**现象**：装了 `ibus-rime`，但 GNOME 输入源里没有 "Rime"。

**原因**：`ibus-rime` 是在 ibus-daemon **启动之后**才装的，新引擎没被加载。

**解决**：
```bash

gsettings set org.gnome.desktop.input-sources sources \
  "[('xkb','cn'),('ibus','libpinyin'),('ibus','rime')]"
```

**另一个坑**：Rime 默认方案 `luna_pinyin` **打出的是繁体**。装雾凇拼音（rime-ice）后需要**重新部署**：
```bash

```
切换简繁：`Ctrl+`` （或 F4 选方案）。

## 九、建图漂移与 EKF 调参（2026-11-14）

> 本章是一次完整的问题定位过程，包含**三个被推翻的错误假设**和一个真正的根因。
> 结论先行：**根因是把 `imu0_queue_size` 从 5 降到 2，导致 EKF 积分失真。**

### 9.1 现象

建图时在**第一次到达直线末端**处突然失去方向，向另一侧偏移，地图完全不可用。

三次建图的地图指标对比（`map_line_quality.py` / `map_defects.py`）：

| 地图 | 尺寸 | 最长直墙 | 平直度 | 已知区域占比 |
|---|---|---|---|---|
| `map_20261106_134147` | 16.2 × 15.0 m | 9.74 m | 4.9 cm | 45.7% |
| `map_20261114_170045` | 17.9 × 10.6 m | 17.91 m | 2.8 cm | 62.7% |
| `map_20261114_174807` | 21.0 × 17.8 m | 13.35 m | 3.6 cm | **36.9%** ⚠️ |

**判读要点**：平直度一直"优秀"，但**已知区域占比骤降**，说明位姿跳变导致地图分叉——
同一块区域被重复扫描到不同位置，互相覆盖成未知。**平直度指标测不出这种问题**。

---

### 9.2 ❌ 被推翻的假设 1：手转测试说明"轮式里程计转向坏了"

**做法**：用手把车原地转 90°，对比三路 yaw。

```
A. 陀螺积分 yaw     : +89.6°    （IMU，准）
B. EKF 输出 yaw 变化: +95.9°
C. 轮式里程计 yaw   :  +1.9°    ← 看起来像"完全测不到转向"
```

**错误结论**：以为底盘 `vz` 坏了，把 EKF 里 `/odom` 的 `yaw_vel` 直接关掉。

**为什么错**：手转时**电机处于使能抱死状态**，轮子被电机扭矩顶住**根本没滚**，
编码器读不到转动是**完全正常**的。这个测试根本无法评价轮式里程计。

> 💡 教训：评价轮式里程计必须让**电机驱动**轮子转起来，手转无效。

---

### 9.3 ✅ 正确验证：电机驱动原地旋转

脚本 `~/rotate_test.py`（左转 90° → 停 → 右转 90° 回原位）：

| 方向 | 目标 | 陀螺 | 轮式 odom | EKF |
|---|---|---|---|---|
| 左转 | 90° | +75.3° | **+70.1°** | **+94.3°** ❌ |
| 右转 | 90° | −71.7° | **−70.1°** | **−98.0°** ❌ |

**两个结论**：
1. ✅ **轮式里程计转向是好的**：±70.1° 完全对称可重复，与陀螺只差约 7%；
2. 🔴 **EKF 输出的 yaw 比两路输入都大 25%~30%** —— 这才是真问题。

---

### 9.4 🔍 定位：EKF 在车停下后还在继续积分

用 `~/yaw_trace.py` 记录时间序列（慢速左转一次，转完停住再观察 3 秒）：

```
t(s)      陀螺积分      odom       EKF
8.30      74.8°      70.6°     60.7°     ← 车已停
8.89      74.6°      70.6°     76.0°     ← 陀螺不动，EKF 还在涨
9.90      74.6°      70.6°     99.6°
10.92     74.6°      70.6°    123.1°     ← 涨到 123°！
```

**静止状态下 EKF 以约 23.6°/s 的恒定速率继续累加 yaw**。
同时验证：IMU 帧率正常（按到达时间积 74.7°、按 header 时间戳积 74.8°，两者一致）。
→ 陀螺数据没问题，是 **EKF 内部积分失真**。

---

### 9.5 隔离实验：把 odom 从 EKF 里完全移除

```yaml
odom0_config: [false,false,false, false,false,false,
               false,false,false, false,false,false, false,false,false]
```

只留 IMU 角速度，转 180° 再测：

```
陀螺积分 +170.0° | EKF +193.1° | 误差 +23.1°
```

**odom 已完全移除，误差反而更大** → 与里程计无关，问题在 IMU→EKF 这一段。

---

### 9.6 ✅ 根因：`imu0_queue_size: 2`

**关键背景**：IMU 是 **100 Hz**，EKF 之前被我改成 **20 Hz**。
一个滤波周期内要消费约 **5 条** IMU 消息。
把 `imu0_queue_size` 从 5 降到 2 后，**大部分消息在队列层被丢弃**，
EKF 用残缺采样序列做数值积分，`dt` 失真 → **角度系统性多积**。

转向时角速度高，误差被放大到 9%~13.5%，累积到地图上就是整体旋转偏移。

**对照实验**（全部为电机驱动的 180° 旋转）：

| 配置 | 陀螺 | 轮式 odom | EKF | EKF 误差 |
|---|---|---|---|---|
| `queue_size: 2` + `freq 20` | +169.5° | +159.9° | **+184.5°** | **+15.0°** |
| 移除 odom + `queue 2` | +170.0° | +159.3° | **+193.1°** | **+23.1°** |
| `queue_size: 5` + `freq 10` | +172.6° | +160.4° | **+174.8°** | **+2.2°** ✅ |
| 恢复 odom + 新协方差 | +170.4° | +160.7° | **+173.7°** | **+3.3°** ✅ |

**修复**：`odom0_queue_size` / `imu0_queue_size` 一律回到 **5**，`frequency` 回到 **10**。

> ⚠️ **重要教训**：`robot_localization` 的 `queue_size` 不要低于
> `传感器频率 ÷ 滤波频率`。100Hz IMU + 10Hz 滤波 → 至少 10 条/周期，
> 给 5 已偏小但可用；给 2 必然失真。想提高滤波频率时必须同步加大队列。

---

### 9.7 ❌ 被推翻的假设 2：JY901 航向角坐标转换错误

**事实**：JY901 节点**根本不发布航向角**：

```
orientation:
  x: 0.0  y: 0.0  z: 0.0  w: 1.0      ← 单位四元数
orientation_covariance:
- -1.0                                  ← ROS 约定：该字段不可用
```

这是当初为了规避磁力计 EMI 干扰的**有意设计**（只输出陀螺/加速度原始值）。
所以"航向角坐标转换"这件事不存在；网页上显示的朝向是 **EKF 对陀螺角速度积分**的结果。

**需要验证的是轴映射与量程**，实测：

| 测试 | 物理转角 | 陀螺积分 | 结论 |
|---|---|---|---|
| 手转 | ~90° | +89.6° | ✅ z 轴=偏航轴、量程 16.4 LSB/dps 正确、符号一致 |

> 陀螺积分长时间漂移是无磁力计 IMU 的**固有特性**，只能靠激光回环纠正，
> 不是坐标转换错误。

---

### 9.8 ❌ 被推翻的假设 3：`link_match_minimum_response_fine = 0.45` 太严

这条**成立**（不是推翻，是确认）。

`0.45` 当初用于抑制转弯拖影，但代价是长直道上重叠区域一少就**匹配失败**，
slam_toolbox 退回纯里程计预测 → 位姿跳变 → 地图分叉。

**已改回 `0.1`**：
```yaml
link_match_minimum_response_fine: 0.1   # 0.45 -> 0.1
```

### 9.9 EKF 最终配置（2026-11-14）

```yaml
frequency: 10.0
two_d_mode: true
map_frame: map
odom_frame: odom_combined
base_link_frame: base_footprint
world_frame: odom_combined

# ---- 里程计：只融合速度类，不融合位置 ----
odom0: odom
odom0_config: [false, false, false,     # x,y,z 位置      ❌
               false, false, false,     # roll,pitch,yaw  ❌
               true,  true,  false,     # vx, vy          ✅
               false, false, true,      # yaw 角速度       ✅（低权重）
               false, false, false]     # 加速度           ❌
odom0_differential: true
odom0_queue_size: 5

# ---- IMU：只用角速度 ----
imu0: /imu/data_raw
imu0_config: [false, false, false,
              false, false, false,      # yaw 姿态 ❌（传感器不输出）
              false, false, false,
              false, false, true,       # yaw 角速度 ✅（主导转向）
              false, false, false]
imu0_differential: false
imu0_relative: true
imu0_queue_size: 5
```

**协方差设置（`can_chassis_bridge.py`）**：

| 数据 | 字段 | 值 | 理由 |
|---|---|---|---|
| `/odom` | pose x, y | 1e-2 | 平动基本可信 |
| `/odom` | pose yaw | 0.5 | 打滑，且未融合 |
| `/odom` | twist vx, vy | 1e-2 | 麦轮打滑有误差 |
| `/odom` | twist yaw_vel | 1e-2 | 实测 160.7° vs 陀螺 170.4°，可用 |
| IMU | angular_velocity | 1e-4 | 实测静止 std≈0.011 rad/s |

> 原来一律写 `1e-3` 是"假自信"。现在按实际可信度区分，
> 让 IMU 在转向上有更大话语权（1e-4 vs 1e-2 = 100:1）。

**关于"同源数据重复利用"**：当前 `/odom` 的位置三项全 `false`，
同一份编码器数据**只以速度形式进入一次**，不存在重复计权。
若将来把位置也打开，才会触发这个风险。

### 9.12 frame_id 语义修正（重要）

**发现**：`can_chassis_bridge.py` 的 `frame_id_odom` 默认值是 **`odom_combined`**：

```python
self.declare_parameter('frame_id_odom', 'odom_combined')
```

于是 `/odom` 消息声称自己的 pose 在 `odom_combined` 帧里。但：

- `/odom` 是**原始航位推算**（从 0 累积、会漂）
- `odom_combined` 是 **EKF 输出、被激光修正过**的帧

两者性质完全不同，共用一个帧名属于**消息语义错误**。

**为什么之前没炸**：EKF 只融合 `/odom` 的 **twist**（车体系，依赖 `child_frame_id`），
`odom0_config` 的位置三项是 `false`。一旦有人打开位置融合，EKF 就会把漂移的
航位推算位姿当成 `odom_combined` 帧的数据，与 SLAM 的修正互相打架。

**修正**（3 处）：

| 文件 | 原值 | 新值 |
|---|---|---|
| `can/can_chassis_bridge.py` | `frame_id_odom: odom_combined` | **`odom`** |
| `ekf.yaml` | `odom_frame: odom_combined` | **`odom`** |
| `ekf.yaml` | `world_frame: odom_combined` | **`odom`** |
| `mapper_params_online_async.yaml` | `odom_frame: odom_combined` | **`odom`** |

修正后 TF 树变成标准结构：

```
map ──(slam_toolbox)──► odom ──(EKF)──► base_footprint
```

`/odom_combined` 仅作为 **EKF 输出话题名**存在，不再出现在 TF 树里。

> 顺便验证了 twist 语义是对的：电机驱动前进时 `twist.linear.x≈0.142, linear.y≈0`
> （车体系）；位置积分确实做了世界系旋转（yaw=54° 时 `Δy/Δx=1.38=tan54°`）。

### 9.14 SLAM 状态监控（补上"黑盒"）

## 33. 【2026-11-15】建图漂移真凶：激光 TF 朝向 180° 错误 + 启动模式陷阱

### 33.1 症状
- 建图时小车一动，`map→odom` 就跳变，日志里成串
  `[MONITOR][JUMP] 位移 0.28~0.36 m`，方向**与小车实际运动方向相反**；
- 地图呈"星芒/扇形"糊掉，未知区域 50~58%，墙线不连续；
- 静止时一切正常（`map→odom` 纹丝不动，说明 TF、雷达、EKF 都不背锅）。

### 33.2 根因：`base_to_laser` 的 yaw = 180° 是错的
扫描帧 `laser` 相对 `base_footprint` 被转了 180°，导致：
- slam_toolbox 用扫描匹配估出来的位姿，**与里程计（odom）先验方向相反**；
- 每一帧匹配都要把位姿"掰回来"，`map→odom` 越攒越大（约 2 倍于实际位移），地图被反复拉扯涂抹。

**实测证据（4 s 直线，指令 0.12 m/s）**

| 项目 | 修正前 | 修正后 |
|---|---|---|
| 实际位移（用 /scan 做 ICP 测得） | 0.40~0.44 m | 0.40~0.44 m |
| /odom 位移 | 0.41 m | 0.41 m |
| `map→odom` 修正量 | **0.71 m，方向与运动相反** | **0.01 m** |
| 原地转 57° 后 `map→odom` yaw 变化 | 跳变 / 反向拉扯 | **0.00°** |

结论：里程计平移本身是准的（与 ICP 差约 10%），雷达数据也稳（静止时相邻帧中位差 1.6 mm），
问题出在 TF 朝向。

| **跟踪精度** | 给正确初始位姿 (0.352,0.022,31.85°)，前进 0.28 m + 转 34° | **0.064 m** | **3.2°** | AMCL 0.519,0.170,56.07° vs 参考 0.577,0.197,52.85° |
| **全局重定位** | `/global_localization`（粒子撒满地图）+ 转 60°、前进 0.5 m、转 −30° | **0.116 m** | **1.6°** | AMCL 0.362,0.710,88.63° vs 参考 0.477,0.697,87.00° |
| **错误初值恢复** | 初值故意偏 (1.5 m, +60°)，协方差 2 m，转 90°+前进 0.4 m | **1.43 m** | **59°** | **未收敛**：AMCL 停在错误区域附近 |

结论：
1. **定位跟踪可靠**：厘米级（6 cm / 3°），可用于后续导航；
2. **"迷路后重定位"用全局定位可行**：约 12 cm / 1.6°；
3. **给一个错误的初始位姿、指望 AMCL 自己纠回来，是无效的**（粒子滤波在这套参数下会卡在错误局部）。
   实际使用原则：要么给**大致正确**的初值（±0.5 m 内），要么先 `/global_localization` 再开一小段。
   若要提高容错，可调大 `max_particles`（3000→5000）与 `recovery_alpha_fast`（0.1→0.2），属参数级调整。

## 35. 【2026-11-15】导航"画龙/反复打方向"分层排查与修复

### 35.1 现象
导航去目标点时路径呈波浪状，车走直线时也反复左右打方向。

### 35.2 按"规划层 / 控制层 / 底盘层 / 定位层"逐层测（全部用同一段 3 m 直线目标）

| 层 | 实测 | 结论 |
|---|---|---|
| 全局路径 `/plan` | NavFn：tortuosity **1.53~2.22**、S 弯 64~71 处；换 SmacPlanner2D 后 **1.001** | **规划层有问题**（NavFn 在膨胀代价场里生成波浪路径） |
| 局部代价地图 | `/scan_filtered` 里仍有 **132 个 0.18~0.19 m 近点**（车体/相机支架自遮挡，遮罩扇区没覆盖 −108° 一带） | 车体自点被标成致命障碍，干扰控制器 |
| 控制器输出 `cmd_vel` | `cmd_wz` 在 ±0.44 rad/s 间周期约 11 s 来回摆，`cmd_vx` 稳定 | **控制层振荡** |
| 底盘执行 `/odom` | `odom_wz` 与 `cmd_wz` 相关 0.87~0.91，幅值一致 | 底盘/电机/编码器正常 |
| 定位反馈 | `/amcl_pose` 与 TF yaw 差 mean1.4°/std4°，最大 14°（AMCL 0.66 s 更新一次） | 有抖动但非主因 |

→ 对应判断表：`cmd_vel 的 wz 本身不断正负变化` = **控制器 + 局部代价地图**。

### 35.3 三处修改
1. 规划器：`NavfnPlanner` → **SmacPlanner2D**（`nav2_smac_planner::SmacPlanner2D`，注意插件名要用 `::`）
   + 全局代价地图 `inflation_radius 0.45→0.35`、`cost_scaling_factor 4.0→2.0`；
2. 两个代价地图的激光观测加 `obstacle_min_range: 0.30`（忽略车体自遮挡近点）；
3. 控制器：`MPPIController` → **DWBLocalPlanner + OscillationCritic**：
   `max_vel_x 0.20 / max_vel_theta 0.40 / sim_time 1.7 / vtheta_samples 40`，
   critics = RotateToGoal, **Oscillation**, BaseObstacle, GoalAlign, PathAlign, PathDist, GoalDist。

### 35.4 修复前后对比（同一条 3 m 直线，目标正前方）

| 横向偏差 max / std | 0.406 / 0.119 m | **0.105 / 0.025 m** |
| 航向摆动范围 | −32.6° ~ +40.6° | **−13.8° ~ +16.8°** |
